# Tests

Plain PHP scripts. Inspect the success marker as well as the exit status: some WordPress scripts return zero even when assertions print FAIL. Database tests are destructive fixtures: use an isolated WordPress/WooCommerce installation, never a live store.

| Script | Network | What it proves |
|---|---|---|

| `test-autopay-safety.php` | WP + WC + DB | Autopay's money-safety edges (146 checks). Claim database errors defer the address (per-address rows, re-checked under the address lock; a deferral that cannot be stored stops expiry for the tick). Claims use a strict insert and never consume against a `cancelling` row. Order events bump the row's `lease_gen` in one statement and leased rows settle only on an unchanged generation, so no event is overwritten and a failure leaves a recoverable lease. Settlement reads storage past WooCommerce's order and HPOS datastore caches (a stale cache would re-run `payment_complete()`), and an unreadable order is not treated as deleted. The cancellation is fenced inside WooCommerce's own save, which also checks the order's stored status and, on refusal, aborts the save rather than writing an older status. Only the canceller's own save approves; a later cancelled save (WooCommerce's HPOS coupon bookkeeping copy, an integration re-saving the order) is allowed only while the order is stored as cancelled, and while both locks are still held, so a stale copy cannot re-cancel a payment saved in between. Nested same-process lock re-entry is refused (a second DB connection plays the other worker). Settlement compares with the exact status read, so custom and filtered-paid statuses settle. Order events run no DDL, even with the `lease_gen` column really missing inside a caller's transaction, and until the migration has recorded itself no lease is settled and expiry starts no cancellation. A failed pause read stops the pass, and a stale "not paused" cache cannot skip the re-read after the lock. The cron fence refuses certification writes inside the statement, direct sweeps certify nothing after a failed safety write, the pause switch stops the job, and the deferral purge pages. Every fix was verified to fail the suite when reverted. Passes under CPT, HPOS with order and datastore caching (compatibility sync off and on), and REPEATABLE READ and READ COMMITTED. Run with `wp eval-file`; a missing `AUTOPAY-SAFETY CHECKS PASSED` banner is a failure. |
| `test-hd-verify.php` | WP + WC + DB | The Privacy Mode verifier and expiry pass, from transaction evidence (134 checks). An order is paid only by confirmed outputs to its own address, received after the binding and owned by no other order. The suite covers the HD safety regression matrix: real payment, historical and mixed history (an old 3800 plus a new 10 credits 10), timing (exact boundary, the block-time slack, first seen unconfirmed, days of downtime), confirmations (and a legacy zero), exact amounts, split payments, output identity, replay against another order or an unknown owner, races with a second connection (the address lock, an order cancelled mid-claim), failures (claim rollback, evidence write, explorer), recovery at each crash point, order states and a changed binding, reorg, expiry (never over pending, failed, underpaid or in-flight), and a BTC Esplora case. It also covers the three findings of the first independent review: a degraded explorer answer never cancels, a busy address completes and a flooded one goes to review, and early-stamped blocks neither end a scan early nor count as old funds. It also covers the second review's findings: a sweep before the checkout records the address, an order paid while expiry reads the chain, and confirmations of a payment below the newest page. Expiry decides only on a fresh scan, never on resumed coverage, and holds too large a history for review. An address the explorer can never list completely goes to review. One unreadable for a day is reported once, and retrying continues. Each wallet's verification, expiry and monitoring pass has its own budget, so a busy wallet cannot starve another, and every attempt is stamped. A completion in flight that can no longer be re-checked keeps its claim, and its order is told. Verification and expiry each carry on where they stopped, per wallet, so neither a slow failure nor the other pass's timestamps can keep the rest from being reached. Every rule was verified to fail the suite when reverted. |
| `test-hd-monitor.php` | WP + WC + DB | Privacy Mode late-payment monitoring, the order-screen panel and log hygiene (37 checks). A late payment to a retired or held address is reported to the merchant once per transaction, with pending and confirmed sightings reported separately. The monitor never completes, cancels or claims anything, so the payment can never pay any order. Receipts from before the order, and evidence already handled while the order was open, are not reported. Monitoring is bounded: a batch per cycle, one check per interval, a 90-day window, a busy address skipped without losing its turn, and a failure still spacing the next attempt; busy and failing addresses stay due but do not hold their place, so a later late payment is still reported. The order panel shows the state, reason and amounts, and escapes them. An invalid key's error carries neither the key nor a stack trace, and cannot abort the background cycle. Every safeguard was verified to fail the suite when reverted. |
| `test-hd-audit.php` | WP + WC + DB (+ WP-CLI) | The read-only `wp nmmpro-hd audit` and the manual `wp nmmpro-hd reconcile` (36 checks). **Audit:** it separates confirmed false positives (every receipt predates the order) from paid orders with absent or insufficient evidence and from vanished credits, and flags unpaid-but-funded orders, reused addresses, pool rows with history, missing orders and disagreeing records. It reports explorer failures as unknown, respects its budget, writes nothing, pages and scopes correctly, and prints no customer details. **Reconcile:** it is a dry run by default and records ownership before acknowledging payment. It refuses malformed ids and transactions owned elsewhere, completes only an order awaiting payment, is idempotent, and never returns an address to the pool. Every safeguard was verified to fail the suite when reverted, except the reconcile refusal, which is backed by the ledger's own refusal and its strict insert. |
| `test-hd-migration.php` | WP + WC + DB | Privacy Mode schema 1.5 and its gate. The 1.4 → 1.5 upgrade runs on scratch tables holding a frozen 1.4 schema. It adds every evidence column, converts a legacy MyISAM table and creates the InnoDB evidence table. It also retires legacy pool and quarantine rows and holds unvalidated in-flight assignments for review. It back-fills nothing, and a refused ALTER or a failed policy write leaves the version unmoved until a retry. No HD address is issued, verified or expired until the schema is ready and the coin has a reviewed evidence adapter. Held rows follow the merchant's own decision on the order, and every row setter is scoped to its wallet. Every safeguard was verified to fail the suite when reverted. |
| `test-hd-allocation.php` | WP + WC + DB | Privacy Mode checkout allocation and non-reuse (69 checks). **Clean check (offline):** a spent zero-balance address or a pending transfer counts as used, and a malformed, partial or wrong-address answer is unknown, never clean. **Allocation:** pool rows with history, explorer failures, reservation and binding failures, legacy rows and rows that don't match the key are never issued, and unknown evidence is set aside within a bounded budget. The chain height is recorded at binding, and no address is bound without it. **Retries and non-reuse:** a retried checkout keeps its address and database-clock boundary, and an ended order's address is never issued again. **Races (second connection):** a held candidate is never taken, a stale worker cannot bind or retire, and a concurrent pool fill is absorbed. **Wallet recovery:** derivation never rewinds, the scan range is reported, and repeated chain history suspends Privacy Mode instead of reusing addresses. Every safeguard was verified to fail the suite when reverted. |
| `test-hd-evidence.php` | WP | The Privacy Mode evidence contract and coin capabilities (116 checks). Two fake explorers page exactly as BlockCypher and Esplora document. **Capability:** every HD coin in the registry has an explicit verdict. **Output identity:** two real outputs in one transaction count as two, spends and outputs to other addresses are ignored, overlapping pages count once, and a disagreeing duplicate or a double spend stops the scan. **Coverage:** a valid empty history is complete. A same-height page boundary loses nothing. A full page at one height, a repeated cursor, a full mempool list or an exhausted page budget is incomplete, and resumed progress converges. **Time:** malformed, non-UTC, future and pre-genesis times are rejected, never replaced with the current time. **Failures:** HTTP errors, malformed JSON, wrong-address answers and bad amounts are never zero. **Sources:** an unreachable source hands over to the next reviewed one, malformed data does not, saved progress is bound to its source and kept through a total outage. **Counters:** a listing shorter than the explorer's own transaction counts (an answer naming only the address, or an empty or cut-short page) is incomplete. **Height floor:** a scan reads down to the height recorded at binding, so an early-stamped block cannot end it early, and a floor above the chain tip is not trusted. **Resumed scans** count transactions exactly across calls: a cut-short or hidden listing is incomplete, and the saved progress is dropped. The count converges, never falsely short, for pages cut part-way through a block and for new blocks arriving between scans. A scan never moves its saved top down (a transaction left out and listed again is not counted twice), marks coverage that relied on saved progress, and converges on dense histories. Every safeguard was verified to fail the suite when reverted. |

CI (`.github/workflows/ci.yml`) runs on push and pull requests: `php -l` across PHP 7.4–8.4, PHPCompatibility (`phpcs.xml.dist`), and the offline HD derivation and address version-byte tests. The release workflow calls this same CI at the tagged commit before publishing.

Additional offline tests cover amount arithmetic, QR payloads, address validation, settings bounds, exchange rates, Solana pagination and pinned HTTP requests. QR image decoding requires zbarimg; a skipped decode is not a successful decode test.

WordPress database tests: `test-sol-retry.php`, `test-autopay-cancel.php`, `test-payment-matcher.php`, `test-autopay-scan.php`, `test-order-init-lock.php`, `test-carousel.php`, `test-hd-verify.php`, `test-hd-migration.php`, `test-hd-allocation.php`, `test-hd-evidence.php`, `test-hd-historical.php`, `test-hd-monitor.php`, `test-hd-audit.php`, `test-consumed-history.php`, `test-payment-integrity.php`, and `test-upgrade-compat.php`. Run each with `wp eval-file tests/<script> --path=<isolated WordPress>` after activating WooCommerce and this plugin. Payment integrity checks cover persistent replay prevention, exact thresholds, interrupted completion, database rollback and history import.
